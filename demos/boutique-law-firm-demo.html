### 3. Explicit "Out-of-Scope" Boundary Definition
To eliminate contractual ambiguity, the following items are expressly categorized as **OUT OF SCOPE** under this SOW:
1. **Third-Party API Fees:** Subscriptions or usage costs for external services (e.g., OpenAI, Stripe, AWS, Twilio) are the direct financial responsibility of Client.
2. **Post-Handoff Content Creation:** Populating ongoing marketing content, product descriptions, or graphic assets not explicitly listed in Section 2.
3. **Legacy Infrastructure Migration:** Refactoring or debugging legacy third-party server environments or undocumented historical databases.
4. **Iterative Design Redesigns:** Once a wireframe/design phase receives Milestone Acceptance, fundamental aesthetic overhauls constitute out-of-scope revisions.

When Client requests features, integrations, or design changes beyond the explicit parameters of the active SOW ("Out-of-Scope Requests"), Provider shall not begin work until a formal Change Order is drafted, priced, and countersigned by both parties.

PROJECT HANDOFF & 30-DAY LIMITED WARRANTY SOP

# PROJECT HANDOFF & 30-DAY LIMITED WARRANTY SOP
**Standardized Project Closure, Repository Transfer & Support Transition**

> This Standard Operating Procedure defines the transition protocol between project completion and post-launch maintenance.

---

### 1. Delivery Handoff Checklist
Prior to final project closure, Provider executes the following handoff protocol:
- [ ] Transfer ownership of primary Git repository to Client organization.
- [ ] Deliver compiled production assets and environment configuration documentation (`.env.example`).
- [ ] Deliver administrative credentials via encrypted vault (e.g., 1Password, Bitwarden).
- [ ] Conduct 60-minute recorded walkthrough demo covering system operations and administrative controls.
- [ ] Countersign the Final Project Acceptance Certificate.

---

### 2. 30-Day Limited Warranty Standard
Provider provides a thirty (30) day Limited Technical Warranty commencing upon execution of the Final Acceptance Certificate:

#### What Is Covered (Free of Charge):
- Correction of verified software bugs or fatal crashes where functionality deviates directly from the signed SOW specifications.
- Restoring broken internal hyperlinks or resolving unhandled database exceptions in delivered code.

#### What Is Excluded:
- New feature requests, aesthetic revisions, or workflow modifications (covered under separate Retainer/Change Order).
- Issues resulting from Client's modification of source code or third-party server environments.
- Breaking changes caused by third-party external API updates (e.g., unexpected OpenAI/Stripe API deprecations).

---

### 3. Transition to Ongoing Retainer
At the conclusion of the 30-day warranty window, support transitions to a dedicated monthly maintenance retainer for priority bug fixes, security updates, and feature iterations.

# WORD-FOR-WORD SCOPE BOUNDARY SCRIPTS
**Executive Email & Verbal Scripts for Protecting Margins & Stopping Scope Creep**

> Use these tested scripts when clients ask for extra work, delay feedback, or push for unpaid revisions.

---

### Script 1: When a Client Asks for an Unplanned Feature Mid-Project
**Context:** The client casually emails: *"Hey, can we also add a live chat feature and multi-currency billing?"*

**The Response:**
> "Hi [Client Name],
>
> That sounds like a great addition to the platform and will definitely enhance the user experience.
>
> Because our active Statement of Work is hyper-focused on launching your core platform by [Target Launch Date], this falls outside our agreed milestone deliverables.
>
> We have two great ways to handle this:
> 1. **Option A (Keep launch date):** We document this in our Phase 2 roadmap and deploy it immediately after launch.
> 2. **Option B (Add now via Change Order):** I can draft a quick Change Order outlining the estimated $[Amount] engineering fee and timeline adjustment to build it into the current sprint.
>
> Let me know which approach works best for your schedule!"

---

### Script 2: When a Client Delays Review & Jeopardizes the Deadline
**Context:** Client hasn't replied to a milestone submission for 4+ days.

**The Response:**
> "Hi [Client Name],
>
> Following up on Milestone #[X] submitted on [Date]. 
>
> To ensure our engineering team remains fully on track for your target launch date of [Target Date], we require consolidated review notes by [Tomorrow, 5 PM].
>
> If you need extra time to test, no problem at all—just keep in mind that under Section 4 of our SOW, each day of review delay adjusts our downstream delivery targets accordingly so we can maintain quality.
>
> Looking forward to your thoughts!"

---

### Script 3: When a Client Pushes for Free Post-Launch Changes
**Context:** Project has been accepted, but the client asks for modifications weeks later.

**The Response:**
> "Hi [Client Name],
>
> Hope everything is running smoothly with the new release!
>
> Taking a look at your request, this represents a new workflow update rather than a defect in the signed SOW deliverables. 
>
> Our 30-day warranty covers bugs within the original scope, but we’d love to help you build this out! We can handle this under our standard maintenance retainer or as a quick standalone milestone for $[Amount].
>
> Would you like me to send over the agreement so we can schedule it?"
